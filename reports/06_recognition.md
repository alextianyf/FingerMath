# 06 · 单数字识别率：上线的新模型

目标：提高游戏里单个手写数字（0–9）的识别率。在 01–04 研究的基础上，确定上线方案，
用游戏自己的浏览器代码端到端量出改动前后的效果。

## 结论

游戏默认模型从 MNIST MLP 换成了一个小 CNN（`digit_model/`）。旧 MLP 还保留着，地址后加 `?model=mlp` 可以切回去对比。

| | 旧 MLP | 新 CNN |
|---|---|---|
| 未见过的书写者（`pad_tmpl`，1 万张） | 92.9% | **96.9%** |
| MNIST 字形 + 游戏笔画（`pad_skel`，1 万张） | 93.9% | **98.0%** |
| MNIST test | 98.3% | 99.5% |
| 游戏实际接受率（屏幕上 2 个答案，`pad_tmpl`） | 93.9% | **98.0%** |
| 打错妖怪（读成了另一个在场的答案） | 0.86% | 0.36% |
| 错了且置信度 > 90% | 4.3% | 0.02% |
| 浏览器端到端（1000 张，游戏 JS 完整管线，WASM） | 93.3% | **96.4%** |
| 下载大小 | 1.7 MB | **223 KB**（float16） |
| 参数量 | 435k | 107k |
| 模型推理（WASM，batch 1） | 0.5 ms | 3.8 ms |
| 一次完整识别（渲染 + 预处理 + 模型） | 6.5 ms | 10.5 ms |

- **上线了两项改动**：
  1. **预处理**：`processing.js` 把 190 px 的字缩到 20 px 时，从最近邻改为面积平均（`resample: 'area'`）。笔画边缘因此是灰度渐变，和 MNIST 一致。
  2. **模型**：notebook 03 的小 CNN，训练数据一半是增强过的 MNIST，一半是"用游戏的笔重新画的 MNIST 骨架"，两种数据都走新的预处理。训练 16 轮，加 label smoothing 0.1。
- 错误率在两个合成测试集上大约降了一半（`pad_tmpl` 7.1% → 3.1%，`pad_skel` 6.1% → 2.0%）。"自信地读错"几乎消失了，这类错误 `decide()` 原本救不回来。
  这里要注意：label smoothing 本身会把最高置信度压到 0.9 左右，所以"> 90%"这一项的下降有一部分来自它，不全是模型变好了。不过"打错妖怪"的比例同样降了，这一项不受置信度刻度影响。
- `decide()` 的阈值不需要改：接受率和打错率都比旧模型好。
- Python 和浏览器的结果一致：同样 1000 张图，Python 96.3%，浏览器 96.4%；导出的 TF.js 模型和 Keras 模型在 32 张检查图上 argmax 完全一致。

## 各项改动分别贡献多少（`pad_tmpl` 是测试集，按 `pad_skel` 选方案）

同样的训练预算（8 轮 × 470 步 × 128），只改一个变量：

| 方案 | MNIST | pad_skel | pad_tmpl |
|---|---|---|---|
| 旧 MLP | 98.28% | 93.90% | 92.88% |
| CNN，游戏原预处理（最近邻，笔宽 18） | 99.08% | 97.13% | 95.29% |
| CNN，面积平均缩放 | 99.21% | **97.57%** | 95.73% |
| CNN，面积平均 + 训练时随机笔宽 ×0.6–1.4 | 99.25% | 97.41% | 95.25% |
| CNN，面积平均 + 笔宽 26 + 随机笔宽 | 99.07% | 97.28% | 95.95% |
| **最终版**：面积平均，16 轮，label smoothing 0.1 | **99.49%** | **97.98%** | **96.91%** |

- 结构（MLP → CNN）和数据贡献最大，这一点 notebook 03 已经说明。
- 面积平均缩放在两个测试集上都带来约 +0.4 个百分点，而且不增加任何成本。
- 随机笔宽、加粗笔画都没有稳定的收益。笔宽 26 在 `pad_tmpl` 上略高，但在验证集 `pad_skel` 上更低，所以没有采用。为了不"在测试集上调参"，方案一律按 `pad_skel` 挑选。
- 训练更久并加 label smoothing 又多了约 +1 个百分点（`pad_tmpl` 95.7% → 96.9%）。
- 测试时平移 5 次取平均（TTA）只多 0.1–0.25 个百分点（`tta.py`），计算量却是 5 倍，不采用。

## 剩下的错误几乎都是"1"

最终版在 `pad_tmpl` 上每个数字的准确率：0–9 依次为 100 / **79** / 100 / 100 / 100 / 100 / **94** / 98 / 100 / 100。

| 易混对（双向合计） | 旧 MLP | 新 CNN |
|---|---|---|
| 1 ↔ 7 | 4.0% | 5.3% |
| 4 ↔ 9 | 2.6% | 0.2% |
| 5 ↔ 6 | 3.4% | 1.2% |
| 0 ↔ 6 | 3.2% | 1.2% |
| 1 ↔ 2 | 2.9% | 3.4% |

4/9、5/6、0/6 基本解决了。剩下的主要是 **带钩、带底座的"1"**（模板书写者里有这种写法）被读成 7 或 2。
所有模型在这上面都只有 70–79%，因为 MNIST 里几乎没有这种 1。
这是数据问题，不是模型问题。合成测试集里的这种写法是我们自己设计的，不能拿它来训练，否则测试集就不再"没见过"了。下一步需要真实数据：

1. 用 `collect/index.html` 采集真实玩家（手指 / 鼠标）的样本，大约每个数字 20 个，作为真正的测试集；如果"1"确实常这样写，再把一部分真实样本加进训练。
2. notebook 04 的个性化：每个数字 5 个样本，在浏览器里约 0.5 秒就能微调完，错误率可以降约 70%。这可以做成游戏里的"校准"功能。

## 怎么复现

```bash
# 研究用 Python 环境：tensorflow 2.21、tensorflowjs、scikit-image、scipy、pillow、pandas
cd mlp_training/research
python build_ship_data.py                    # 三种预处理变体的数据集（cache/ship_*.npz，约 30 分钟）
python train_ship.py                         # 4 个对比方案 → results/06_single.json
python train_ship.py final                   # 最终版（按 pad_skel 选预处理）
python export_ship.py ship_cnn_final area18  # → /digit_model（float16）和 export/ship_check.json
python export_e2e.py                         # → e2e/fixtures.json（1000 张 pad_tmpl 的原始笔画）
python tta.py ship_cnn_final area18          # 测试时增强的对比
```

浏览器端：在仓库根目录启动任意静态服务器，例如 `python -m http.server 8000`，然后打开：
- `/mlp_training/research/e2e/`：用游戏自己的 `pad.js` / `processing.js` / `recognizer.js` 跑 1000 张图，输出准确率、易混对和延迟；加 `?model=mlp` 测旧模型。结果在 `results/06_e2e_*.json`。
- `/mlp_training/research/export/bench.html`：各模型的纯推理延迟，以及导出结果和 Python 是否一致。
- `/?debug`：游戏本身。AI 面板右上角显示后端和延迟，鼠标悬停可看到用的是哪个模型。

## 多位数（已暂停）

按决定暂停了。原型保存在 `recognition-multidigit-wip` 分支：笔画按横向重叠分组，每个数字单独过 CNN，再结合屏幕上的答案判定；用 `?multi` 开启游戏模式。
初步数据（旧 MLP，浏览器端到端）：两位数整串全对 85.4%，三位数 83.0%，拆分位数的正确率 98–99%。另一个研究分支（`claude/cnn-research-145fc2` 的 notebook 05）用 CNN 在 Python 里比较了几种做法：笔画分组 + 单数字 CNN 整串全对 87.6%（两位数 90.7%，三位数 84.3%），CTC 序列模型 88–92%，连通域分割只有 67%。
逐位识别率提高后整串准确率会跟着提高（约等于单数字准确率的 n 次方），所以先把单数字做好也是多位数的前提。
